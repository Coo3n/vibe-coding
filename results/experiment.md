## 3. Перезапуск после инструмента

После нового запуска: **9 сообщений**, отпечаток **`fb56314469b1`**. Исторический поиск показан с пометкой «ИЗ ИСТОРИИ — не новый вызов».

## 4. Изменение условий и пустая выдача

- Бюджет изменён на 150 000 ₽, прочие условия сохранены. Модель выполнила поиск с новым бюджетом, результат — только TR-001 за 145 000 ₽.
- Бюджет изменён на 1 000 ₽ без изменения остальных условий. В аргументах инструмента именно **1000**, выдача пустая. Агент не придумал предложения и не ослабил фильтры.
- Наблюдение: в тексте пустой выдачи модель начала фразу «Проверил с бюджетом 100 000 ₽... точнее, 1 000 ₽». Эта оговорка не скрывается: фактический вызов инструмента использовал 1000, а модель сама исправилась. Сохранение контекста не гарантирует безошибочного текста LLM.

## Дополнительные требования: строгий JSON и 606 путёвок

По просьбе пользователя ответы API переведены на строгий JSON. Ниже этап проверки промежуточной реализации с action ask/search/answer. Затем по отдельному запросу пользователя режим заменён на required на каждом запросе с инструментом respond_to_user — итоговый контракт описан в последнем разделе.

Обнаруженные проблемы не скрывались:

- Первые два прогона со строгой схемой и tool_choice=auto выдавали корректный JSON «ищу», но инструмент не вызывался. Поэтому эти прогоны не считаются успешной демонстрацией поиска.
- Прямой реальный запрос с tool_choice=required вернул настоящий search_tours. В агент добавлен переход action=search → обязательный вызов инструмента → финальный JSON. Это дополнительный HTTP-шаг, не попытка имитировать результат функции.
- Следующий прогон выполнил инструмент, но модель добавила вымышленный TR-003/Rixos за 198 400 ₽, которого в результате не было. Такой прогон не считается успешной проверкой точности. Усилена инструкция опираться на tool. Попытка regex-проверки ID отменена после ревью: она считала выдумкой даже честный ответ «TR-003 отсутствует в результатах». - Ревью выявило падение replay при features=null в повреждённой истории. Сценарий воспроизведён, после исправления подобные поля отклоняются при чтении через HistoryError, без изменения файла. Проверены также неверные типы meal и price_total.

## Итоговое требование: required на каждом запросе

По отдельному запросу пользователя auto полностью исключён. Модель выбирает один из двух strict-инструментов: search_tours для поиска либо respond_to_user для JSON-вопроса/ответа. Поиск имеет nullable необязательные поля, но в его strict-схеме все поля присутствуют. Ответ имеет action (ask/answer) и answer; в истории сохраняются исходные аргументы и tool-подтверждение accepted. Обычный текст без вызова отвергается, перехода к auto нет.

Реальный API-прогон с загрузкой нового экземпляра агента из JSON подтвердил:

- Уточняющий вопрос: только respond_to_user, режим API `[required]`.
- Поиск: search_tours → respond_to_user, режимы API `[required, required]`, возвращены TR-001 — 145 000 ₽ и TR-002 — 178 000 ₽.
- После восстановления: messages равны сохранённым. Воспоминание выдачи: только respond_to_user, режим `[required]`, верные ID, цены, характеристики и разница 33 000 ₽, без нового search_tours.

Сводка теперь включает технический инструмент ответа, поэтому «без нового поиска» означает ноль вызовов search_tours, а не ноль всех tool_calls. Локальный протокол: `results/local-task-7/13-required-every-request.ansi`.
