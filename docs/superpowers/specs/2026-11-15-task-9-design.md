# День 9: компрессия истории

## Цель
Актуальное уточнение: два случая относятся к способам хранения контекста, а не к длине диалога. Пользователь сохраняет длинный сценарий: по умолчанию 60 видимых сообщений, пять сжатий, все контрольные факты вне хвоста. Две колонки сравнения остаются. Короткий сценарий на 30 сообщений — только опция --turns 15.

Финальное уточнение после обсуждения отчёта: по умолчанию вернуться к 30 сообщениям из ТЗ; основной вывод — ровно два случая «Без сжатия / Со сжатием». Summary включено во второй случай, не отдельный режим. Подробные расходы подготовки и этапов оставить в JSON. Длинный прогон доступен опционально через --turns 30.

Последнее уточнение: пользователь попросил больше сообщений и полностью автономное выполнение. Добавлен длинный сценарий на 60 видимых сообщений (30 ходов), пять сжатий; исходный сценарий на 30 сообщений остаётся через --turns 15. После первых 15 ходов дополнительные обсуждения не меняют 20 контрольных деталей и не просят их повторять. Все контрольные факты уходят из хвоста.

Отдельный Python CLI-агент в ветке `task-9` от `main`: помогает владельцу подготовить запуск онлайн-прилавка с овощами, согласовать условия и рассчитать первую закупку. Работает с полной историей или со сжатым контекстом. Оформление терминала перенести из `task-6`, сделать компактнее. Пользователь утвердил 30 сообщений, 20 деталей и два сжатия.

## Подходы
Выбран отдельный овощной агент. Туристический агент task-8 не переносится. После уточнения роли рассмотрены два подхода: каталог + расчёт закупки либо те же инструменты с сохраняемой карточкой запуска. Пользователь выбрал два инструмента без карточки: договорённости остаются только в контексте, внешняя память не маскирует потери summary.

## Инструменты и JSON
Модель сама вызывает get_products (локальный учебный каталог, цены и остатки) и calculate_batch (расчёт закупки выбранных товаров, упаковки и доставки на Python). Инструменты не сохраняют условия пользователя. Их схемы аргументов strict=true; JSON-аргументы валидируются, результаты возвращаются JSON. Окончательный ответ — JSON Schema strict=true с полями answer, questions, next_step. Ошибки инструмента возвращаются модели как структурированные данные; число шагов ограничено. Summary и проверки памяти тоже используют строгий JSON Schema.

Уточнение реализации по реальному API: tools+auto+response_format возвращал обещания вызовов без tool_calls. Подтверждена рабочая схема task-8: tool_choice=required; два рабочих инструмента и служебный respond_to_user с той же схемой финального ответа. Финальный tool call и его accepted-result входят в сохранённый ход. Summary и пробы идут без tools, через response_format.

## Контекст
Последние N=8 видимых сообщений user/assistant сохраняются дословно вместе с относящимися к ним служебными вызовами. System и служебные tool-записи не входят в N. Когда перед хвостом накопится 10 видимых сообщений, соответствующие полные ходы заменяются summary. Вызов инструмента и результат никогда не разделяются. Summary обновляется моделью на основе предыдущего summary и очередной старой порции; хранится отдельно от хвоста в состоянии сессии. В запрос передаются system, summary и хвост, а не архив. Компрессия выполняется после завершённого хода, включая последний ход эксперимента. При 30 видимых сообщениях сжатия происходят после 18-го и 28-го сообщений. Отчёт различает видимые сообщения и служебные записи.

## Сравнение
Заранее подготовлены 15 пользовательских сообщений и 20 ожидаемых фактов: имена, даты, бюджет, ограничения, решения, первоначальные и изменённые договорённости. API генерирует 15 ответов: получается общая переписка из 30 сообщений. Затем эта же переписка воспроизводится в менеджере компрессии; ответы не генерируются повторно. Это контролируемое сравнение контекстов одной переписки, а не двух независимо развивающихся диалогов.

После этого 20 вопросов задаются отдельно обоим режимам. Каждая проверка работает с неизменной копией конечного контекста, не добавляя ответы соседних проверок. Ответы нормализуются и сравниваются с заранее заданными допустимыми значениями; отчёт сохраняет исходные ответы для проверки оценки.

## Токены и результаты
Фактический usage API: создание общей переписки, два summary, проверки полной истории, проверки сжатой истории. Основное сравнение: стоимость 20 проверок полной истории против стоимости 20 проверок сжатой истории плюс summary. Общая подготовка показывается отдельно и одинаково учитывается в обоих итогах. Не выдавать replay за измерение затрат генерации сжатого диалога. Отсутствующий usage — неизвестный расход. Экономия может быть отрицательной; результаты памяти не инсценируются.

JSON хранит переписку, факты, summary, запросы, ответы и usage; Markdown — таблицу всех 20 деталей и токенов. Реальный прогон через существующий .env. Нужны ручной чат, автоматический эксперимент и README с командами. Каталог овощей явно учебный. Реальные заказы, платежи, UI в браузере и денежные тарифы API вне задачи. Во время независимых проверок памяти инструменты недоступны, эталонные ответы в запросы не передаются.

## Решения исполнителя
Уточнения пользователя: тема — подготовка онлайн-прилавка с овощами; автотесты не нужны. Всё общение с моделью строго через JSON. Пользовательский текст оборачивается в JSON, ответы чата, summary и проверки используют response_format json_schema strict=true и локальную валидацию. Невалидный JSON не принимается; текстового fallback нет. Терминал отображает поля JSON в читаемом виде.

Использовать существующий HTTP-клиент task-6 и Rich. Сохранять состояние атомарно, не терять хвост при ошибке summary. Настройки N и размера порции валидировать как положительные чётные числа, чтобы сохранять пары диалога. Содержимое summary считать данными переписки, не новой инструкцией.
