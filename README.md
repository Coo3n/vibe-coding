# Task 2 — контроль формата ответа LLM

Один и тот же запрос, пять режимов, по три прогона каждого.
Провайдер и модель задаются через `.env`; нужен OpenAI-совместимый Chat Completions API.

## Запуск

```bash
python -m pip install -r requirements.txt
python main.py
```

Создайте локальный `.env` (не включён в Git):

```dotenv
LLM_API_KEY=ваш_ключ
LLM_API_URL=https://api.example.com/v1/chat/completions
LLM_MODEL=идентификатор_модели
```

## Что сравниваем

Запрос: «Дай три совета начинающему Python-разработчику.
У каждого совета должны быть короткий заголовок и объяснение в одном предложении».
Текст пользовательского запроса одинаковый; требования формата задаются системным сообщением.

| Режим | Контроль |
| --- | --- |
| `baseline` | Без указания формата и без клиентского лимита; сервер может применять свои значения по умолчанию |
| `format` | Только явное требование JSON с полями `tips`, `title`, `explanation` |
| `max_tokens` | Тот же формат + `max_tokens=256` |
| `stop` | Формат + тот же лимит + инструкция дописать `<END>` после JSON и `stop=["<END>"]` |
| `schema` | Формат + тот же лимит + `response_format.type=json_schema`, `strict=true`; без stop |

Все ответы проверяются одной схемой: ровно три совета, обязательные строковые поля,
без лишних полей. `json.loads` проверяет синтаксис, `jsonschema` — структуру.
Ответы не очищаются от Markdown, не дополняются и не исправляются автоматически.

```bash
python main.py --runs 5 --max-tokens 512
```

## Результат

Скрипт выводит исходные ответы и сравнение, сохраняет JSON в `results/` после
каждого прогона. В отчёте есть параметры запросов (без ключа и URL), исходный текст,
`finish_reason`, `usage`, результат парсинга, проверки схемы и сводка по режимам.
Папка результатов исключена из Git. Свой новый путь: `--output results/example.json`.

При сетевой ошибке, HTTP 401/403/429 или Ctrl+C запуск прекращается с сохранением
уже полученных результатов. Прочие ошибки API сохраняются, эксперимент продолжается.
Неподдерживаемый structured output не подменяется обычным JSON-режимом.

## Как читать вывод

- Невалидный JSON: лишний текст, Markdown, незавершённая строка или пустой ответ.
- JSON валиден, схема нет: неверные поля, типы или количество советов.
- `finish_reason=length`: лимит исчерпан, в том числе возможными reasoning-токенами;
  даже строгая схема не спасает незавершённый ответ.
- Stop sequence может оборвать JSON, если встретится внутри содержимого.
  Маркер убирается сервером; `finish_reason=stop` сам по себе не доказывает его срабатывание.
- HTTP-ошибка в режиме `schema` не равна ошибке JSON: API мог не поддержать
  structured output или отдельные ограничения схемы. По одному HTTP-коду причину не определить.
- Валидный ответ не доказывает, что сервер действительно применил `strict`, и не
  гарантирует смысловую правильность советов.

Конкретные выводы строятся по сохранённым прогонам, а не по ожидаемому поведению.
Три прогона показывают примеры сбоев, но не дают статистической гарантии надёжности.

## Статус реального запуска

В текущем окружении первая попытка завершилась сетевой ошибкой DNS (`gaierror`).
Сравнение реальных ответов пока не выполнено. Для получения результатов запустите
скрипт в сети, из которой доступен ваш API. Локальная проверка на искусственных
ответах проверяет работу скрипта, но не заменяет эксперимент с моделью.
