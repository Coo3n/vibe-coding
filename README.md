# День 9 · Овощной прилавок и сжатие истории

Агент помогает владельцу подготовить запуск овощного онлайн-прилавка: согласовать
ассортимент, бюджет, сроки и доставку, рассчитать первую закупку. Python CLI,
реальные запросы к OpenAI-совместимому API, строгий JSON и настоящие tool calls.

## Запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python main.py
```

В `.env`: `LLM_API_URL` (полный адрес `/chat/completions`), `LLM_API_KEY`,
`LLM_MODEL`. Файл с ключом не входит в Git. API должен поддерживать tools,
`tool_choice=required`, JSON Schema и `strict=true`.

В меню: **1** — эксперимент; **2** — чат со сжатием; **3** — без сжатия.
В PyCharm достаточно запустить `main.py`.

```bash
python main.py --demo                         # по ТЗ: 30 сообщений, два случая
python main.py --demo --turns 15              # те же 30 сообщений (по умолчанию)
python main.py --demo --turns 30              # дополнительный длинный: 60 сообщений
python main.py --chat                         # ручной чат со сжатием
python main.py --chat --mode full             # полная история
python main.py --demo --model coder-mini      # другой маршрут модели
python main.py --chat --keep-last 8 --compress-every 10
```

Настройки N и размера порции — положительные чётные числа, потому что сохраняются
завершённые ходы. Для другой настройки используйте новый `--session путь.json`.
Папка `--output-dir` для `--demo` должна быть новой, чтобы не перезаписать прошлый прогон.

## Для чего инструменты

| Инструмент | Что делает |
|---|---|
| `get_products` | Возвращает учебный каталог овощей, закупочные цены и остатки |
| `calculate_batch` | Проверяет количество и остатки, считает закупку + упаковку + доставку на Python |
| `respond_to_user` | Служебный канал ответа: JSON с `answer`, `questions`, `next_step` |

Модель сама выбирает инструмент и аргументы. Все вызовы реальные, через `tool_calls`;
одного текста «сейчас посчитаю» недостаточно. В чат-запросах используется
`tool_choice=required`: финал тоже передаётся вызовом `respond_to_user`.
Цены и остатки учебные; инструменты не оформляют заказы и не хранят договорённости пользователя.

Пользователь пишет обычный текст — программа оборачивает его в JSON `{"message": "…"}`.
Аргументы инструментов, результаты, ответы, summary и проверки памяти — JSON.
Ответы валидируются локально; markdown-блоки и обычный текст вместо JSON не принимаются.
Терминал показывает поля JSON читаемыми блоками в стиле `task-6`.

## Как устроено сжатие

1. Храним последние **N=8 видимых сообщений** без изменений, включая связанные tool calls.
2. Когда перед хвостом накопилось **10 старых видимых сообщений**, отправляем их
   отдельным запросом к той же LLM вместе с предыдущим summary.
3. Модель возвращает JSON `facts`, `decisions`, `open_questions`.
   Инструкция просит сохранить точные детали и различать прежние и актуальные договорённости.
4. Только после валидации заменяем старые ходы новым summary. В следующий запрос
   идут системная инструкция, отдельное summary и несжатый хвост — не весь архив.

Видимое сообщение — реплика пользователя или финальный ответ агента. Служебные
tool-записи не увеличивают этот счётчик и уходят в summary вместе со своим ходом:
вызов и результат никогда не разрываются. **N — минимальный несжатый хвост**:
между сжатиями он растёт до накопления очередной порции. При 30 сообщениях сжатия
происходят после 18-го и 28-го; при 60 — после 18, 28, 38, 48 и 58-го.
В конце обоих сценариев остаётся summary + 10 видимых сообщений.

Сессии: `data/session-compressed.json` и `data/session-full.json`.
Summary хранится отдельным полем `summary`, хвост — в `turns`.
Сохранение атомарное. При ошибке API/JSON/сохранения ручной ход не фиксируется;
предыдущий контекст остаётся доступен. Потраченные на неудачный ход токены показываются,
если API сообщил usage.

Команды чата:
- `/summary` — посмотреть сохранённое summary, не новый запрос к LLM;
- `/history` — посмотреть несжатые ходы;
- `/new` — очистить текущую сессию;
- `/exit` — выйти.

Сжатие автоматическое. `/compact` — возможная команда приложения, а не параметр
Chat Completions API; здесь её роль выполняет счётчик и `Context.compress()`.

## Эксперимент по ТЗ

**По умолчанию 30 видимых сообщений: 15 пользовательских + 15 ответов**, как в ТЗ.
`--turns 30` запускает дополнительный вариант на 60 сообщений. Дополнительно сохраняются
служебные вызовы инструментов. До первого запроса фиксируем **20 деталей**:
имя, название, исходные и изменённые сроки/бюджеты, поставщик, район, условия
доставки, упаковка и запрет пластика, платформа, оплата, ответственный,
количество картофеля, результат расчёта и рекламное решение.

Для честного сравнения:
- генерируем **одну реальную переписку**, включая каталог и расчёт;
- воспроизводим те же ходы в менеджере компрессии — получаем пять summary
  в длинном режиме, два в коротком;
- задаём **20 отдельных вопросов** к каждому конечному контексту;
- каждый вопрос получает независимую копию контекста: другие проверки не освежают память;
- инструменты в проверках недоступны, эталонные ответы не отправляются модели;
- фиксируем точное совпадение с заранее заданными вариантами, `null` и несовпадения.

Иные формулировки помечены «требует сверки»: это не автоматическое доказательство
забывания. В отчёте видны исходные ответы, а не только баллы.

Длинный сценарий добавляет обсуждение карточек товара, приёмки, остатков и
обратной связи, не меняя контрольные договорённости. В нём все 20 исходных деталей
успевают покинуть несжатый хвост. От начала диалога до итогового отчёта эксперимент
проходит без ввода пользователя.

## Как читать токены

В терминале и Markdown-отчёте **только два сравниваемых случая**:

| | Без сжатия | Со сжатием |
|---|---|---|
| Что отправляем с вопросом | Всю переписку | Summary + последние сообщения |
| Что проверяем | Те же 20 деталей | Те же 20 деталей |
| Что входит в итог токенов | Все 20 вопросов и ответов | Все 20 вопросов и ответов + создание summary |

Summary — часть второго случая, не третий режим. Строка «Из них создание summary»
показывает уже включённый расход: повторно прибавлять его нельзя.
Вход и выход берутся из фактического usage API. Подготовка исходного диалога
выполняется один раз; подробный технический учёт всех этапов остаётся в JSON.

Общая подготовка также включена одинаково в два итоговых режима. Их нельзя
складывать: они перекрываются по подготовке. Есть отдельная строка фактического
расхода всего эксперимента. Отсутствующий usage — `?`, не ноль. Кэшированные токены
уже входят во вход; стоимость в деньгах не рассчитывается.

Это измерение стоимости повторных обращений к **одной готовой переписке**.
Replay не измеряет генерацию второго независимого диалога со сжатым контекстом.
Ручной чат, в отличие от replay, действительно сжимает контекст по ходу общения.

`app/cli.py` — терминал. Автотесты не добавлены по запросу пользователя.
